# Quirón OS repository architecture

This describes the architecture implemented through Phase 1.0A, not planned CRM functionality. The approved stack in this repository is Nx 22, Node 22, TypeScript 5.9.3, npm workspaces, ESLint, and native `node:test`. The monorepo has six production projects: applications `api` and `web`; modules `core`, `ambassadors`, `tasks-agenda`, and `seguros-marketing-leads`. The API serves `/health` and JSON 404 responses. Web and the four module production entrypoints remain shells.

## Dependencies and consumption

Each project has one governing layer tag. `layer:module` projects cannot import other modules; they may depend on future `layer:infrastructure` packages. Infrastructure may depend only on infrastructure. `layer:app` projects may compose module and infrastructure public roots. The retained `type:*` and `source:*` tags classify projects but do not grant import permission. Core is a module implementation, and Tasks/Agenda is an operational shared capability; neither is a generic contracts package. No production infrastructure or contracts package exists.

The four modules are npm workspaces with public `@quiron/*` package roots. Each package exports only `.` from its project-local built output. `npm ci` creates native workspace links; library builds produce JavaScript and declarations before consumers use them. TypeScript source aliases and runtime alias loaders are absent. The API build emits to `dist/apps/api/`, Web to `dist/apps/web/`, and the API test target separately declares `dist/test-fixtures/api/` for its compiled consumer fixture. The API's current graph edges to all four libraries come from that test fixture, not production API composition.

Nx and ESLint enforce dependency direction, public entrypoints, deep-import and cross-project filesystem restrictions. Production source uses static imports; dynamic and native loaders are restricted. Small inline rules close documented Nx missing-graph, opaque runtime-access, and same-project generated-output/test-tooling gaps. JavaScript under each project's root `test/` directory receives limited loader permissions while retaining layer and public-entrypoint checks; `src/test/` and stray `*.test.mjs` files do not receive those permissions. The workspace verification directory `tools/test/` is separate from project tests. Existing harness path exceptions are exact and source-scoped. These static checks govern reviewed code, not hostile JavaScript execution.

## Verification and limits

Run `npm ci` and `npm run check` with Node 22. The gate preflights the six projects and real targets, lints project and verification code, typechecks, builds, runs native `node:test` suites with fail-closed file discovery, and repeats the boundary matrix. Run `npm run check:projects` before standalone ESLint so the Nx graph is available; otherwise lint fails closed. CI runs the full gate with Nx daemon, cloud, cache, and TUI disabled. Tests exercise the actual API package consumer and runtime behavior, but architecture probes do not provide CRM functionality coverage.

Consumers need workspace links and built declarations. The Web shell has no browser build or deployment packaging. The path guard is lexical, and runtime-loader enforcement is conservative and version-sensitive. Event Envelope V1, an event backbone, persistence, AI orchestration, and CRM business processes are not implemented. Historical decisions, verification, and detailed limitations are in [Spec 001](../specs/001-architecture-foundation/spec.md) and [Spec 002](../specs/002-architecture-hardening/spec.md).
