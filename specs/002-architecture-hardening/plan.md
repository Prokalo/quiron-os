# Spec 002 — Technical plan and decisions

Baseline: `dbc3d1259f5a0b9d9e1030c593fe71775f6f35a3`. The [published decision at `9952cea`](https://github.com/Prokalo/quiron-os/blob/9952cea3885a2d10b9e7a43248813001e17b24a0/docs/decisions/0001-phase-1-0a-architecture-remediation.md) gave the before/after rationale: close observed dependency, runtime-linking, output, and verification gaps without changing the six production source entrypoints or adding business behavior.

## Ownership and imports

Core, Ambassadors, Tasks/Agenda, and Marketing Leads are `layer:module` implementations. Modules may depend on future `layer:infrastructure` packages but never other modules, even through another module's public facade. Future infrastructure may depend only on infrastructure; applications may compose module and infrastructure public roots. Existing `type:*` and `source:*` tags remain classifications, not permission gates. Core is not a generic contracts package, and Tasks/Agenda's operational sharing does not make it infrastructure. Future shared contracts require independent ownership; no such package was added.

Native Nx `@nx/enforce-module-boundaries` handles layer direction, buildability, cycles, and cross-project relative paths. ESLint import/syntax rules and package exports allow only declared `@quiron/*` package roots and block unknown names, deep imports, absolute/file-URL/workspace-root paths, and unsupported dynamic/Native loaders. Production imports are static. The explicit npm workspace manifests supply the public-root allowlist. A small Nx wrapper turns the observed missing-graph empty-listener behavior into an error. Small inline rules reject opaque access to ambient runtime loader objects and same-project generated-output or production-to-root-test imports; the latter is lexical, not a custom resolver. These checks are architecture controls, not a security sandbox.

JavaScript in each project's root `test/` directory gets native-loader permissions only: layer direction, public roots, and literal dynamic/CommonJS workspace import restrictions remain. `src/test/` and stray `*.test.mjs` files do not receive these permissions; workspace verification under `tools/test/` is distinct. TypeScript consumer fixtures retain production restrictions. Each existing `test/boundaries.test.mjs` has only its exact import of the boundary helper; only the API consumption test may load its exact compiled fixture. Other filesystem imports into generated output or tooling remain forbidden. Production cannot import its project's root `test/` directory. Executable JS/MJS/CJS/JSX across `apps/`, `modules/`, and future `packages/` follows the same policy outside these narrow test exceptions.

## Linking, outputs, and validation

Register the four modules as npm workspaces; each exposes only `.` through `main`, `types`, and `exports` pointing to its local `dist/`. Remove TypeScript source aliases. Use plain `tsc -p` with `rootDir: src`, project-owned `outDir`, JavaScript/declaration output, and no-emit typechecks. API, Web, and API test-fixture outputs remain disjoint. Builds depend on dependency builds; native Node resolves package links created by `npm ci`. The Core/API proof with `paths: {}` preceded migration of the other three libraries. Current API-to-library graph edges originate in a test fixture, not production composition.

`check:projects` reads a fresh Nx graph and requires the six projects, valid layer tags, real lint/typecheck/build/test targets, disjoint declared build outputs, exact executable test command shapes, finite uncached tests, and build prerequisites. `npm run lint` covers projects and tools/config; `npm test` runs tooling tests and all six project tests; `check:boundaries` runs the full matrix; `npm run check` combines them. Native `node:test` with checked file discovery and per-file summaries rejects empty, skipped-only, TODO-only, cancelled, and failing suites. CI uses Node 22 and disables Nx daemon/cloud/cache/TUI. Disposable copies exercise missing/disabled guards and real project-root JavaScript without mutating production sources.

No bundler, runtime alias loader, custom dependency resolver, installed ESLint plugin, test preload, or new application framework was introduced. Deployment/browser packaging and dynamic-loading requirements remain future decisions.
